# Decisions & Learning Log

Dated entries capturing real decisions made on this project and why — not a changelog of code, a record of *reasoning*, so a future reader (including future-me) doesn't have to reconstruct it from scratch.

## 2026-07-20 — Python 3.12 over the system Python (3.9.6)

macOS ships Python 3.9.6 as its system Python. It's past its official end-of-life (Oct 2025) and not meant for real development — installing project packages into it risks conflicting with what macOS itself relies on. Installed Python 3.12 via Homebrew and built the project's `.venv` from that instead. Chose 3.12 specifically over the newest (3.14) since some ML libraries we'll need later (sentence-transformers, chromadb) sometimes lag behind brand-new Python releases.

## 2026-07-20 — Raw SQL via `sqlite3`, not an ORM

An ORM (Object-Relational Mapper) would generate SQL for us behind the scenes. Deliberately avoided one — this project exists partly to actually learn SQL, and an ORM would hide exactly the thing being learned.

## 2026-07-21 — `workspace` column instead of full user authentication

Papers need to be separable by who uploaded them (e.g. a friend uploading dengue papers shouldn't mix into a maternal-mortality collection), but full login/auth is explicit non-MVP scope. Solution: a single `workspace` text column on the papers table — one column, many possible values across rows, filtered with `WHERE workspace = '...'`. Scales to any number of people with zero schema changes, unlike a naive "one column per person" spreadsheet-style design.

## 2026-07-21 — Requirements added incrementally, not front-loaded

`requirements.txt` starts empty. Each dependency gets added at the roadmap step that actually needs it, so its purpose is clear when it's added rather than installing a wall of unused packages on day one.

## 2026-07-23 — Papers schema fields, informed by real bibliographic standards

Researched what real reference managers (Zotero, Mendeley) and metadata standards (Dublin Core, DataCite, CrossRef) actually capture for a paper. Added `journal`, `doi`, and `abstract` beyond the original title/authors/year — `abstract` specifically because it lets the UI show a quick summary without running full RAG retrieval, and `journal`/`doi` because they're what makes a citation look real. Deliberately left out `volume`/`issue`/`pages` (matter for perfect citation formatting, not for retrieval quality) and `keywords` (our retrieval is semantic/embedding-based, not keyword-based, so a keywords column is less load-bearing here than in a traditional reference manager). Schemas are cheap to extend later — this isn't a permanent decision, just the right scope for now.

## 2026-07-23 — `id` (surrogate key) and `doi` (natural key) are both needed

They look redundant but serve different jobs. `id` is internal, always present (auto-assigned on insert), used for relationships between tables later. `doi` is an external, real-world identifier — not guaranteed to exist (many papers don't have one), not something we control, but useful later for detecting duplicate uploads and linking to the original source. Standard database pattern: prefer a surrogate key as the actual primary key even when a natural key exists, because natural keys can be missing or fragile to match on.

## 2026-07-23 — Parameterized queries (`?` placeholders), never string-built SQL

All queries in `app/db/queries.py` pass values as a separate tuple to `.execute()`, never by pasting values directly into the SQL text (e.g. an f-string). Directly pasting user-controlled text into SQL is how SQL injection attacks happen — a paper title containing something like `'; DROP TABLE papers; --` could otherwise be interpreted as a second command instead of a piece of data. Placeholders guarantee values are always treated as data, never as part of the command structure, regardless of their contents.

## 2026-07-24 — `pypdf` for PDF text extraction, chosen over `pdfplumber`

`pypdf` is lightweight and does exactly what we need — extract raw text. `pdfplumber` is more powerful (handles complex layouts and tables precisely) but heavier, and we don't need that level of power for the MVP. Tested against a real academic paper (dengue/climate paper, ~80K characters) — extraction was clean, no garbled text.

**Known limitation, accepted for now:** `pypdf` only extracts text that's actually embedded as selectable text in the PDF. A scanned paper (a photograph of a page, not real typed text) would extract to empty or near-empty output — `pypdf` can't do OCR (recognizing text from an image). Out of scope for the MVP; would need a different tool (e.g. `pytesseract`) if this becomes a real problem with actual uploaded papers.

## 2026-07-24 — Fixed-size chunking, no overlap (for now)

`chunk_text()` splits paper text into equal-sized pieces with no overlap between them. A more refined technique gives neighboring chunks a bit of shared overlap, so a sentence that would otherwise get cut in half at a chunk boundary still appears in full somewhere. Deliberately skipped for now to keep Step 4 (already the densest step on the roadmap) from getting even more complex on the first pass. Revisit if retrieval quality later seems to miss things right at chunk boundaries.

## 2026-07-28 — Run project files with `-m`, not as a bare script path, once they import our own code

`python app/rag/chunking.py` failed with `ModuleNotFoundError: No module named 'app'` the first time a file tried to import our own project code (`from app.ingestion.pdf_extractor import extract_text`). Running a file directly as a script makes Python search for imports starting from *that file's own folder*, not the project root — so it couldn't find `app/` at all. Fix: run it as a module instead, `python -m app.rag.chunking` (dot notation, no `.py`), which searches starting from the current working directory (the project root) instead. Files that only import third-party/stdlib packages (`schema.py`, `queries.py`, `pdf_extractor.py`) never hit this, since those are always found regardless of the search starting point — this only shows up once a file imports *our own* project structure.

## 2026-07-29 — First real RAG retrieval test: works, with a known weakness

Tested `search()` end-to-end against the real dengue paper with the query "mosquito breeding and rainfall" — deliberately not using the paper's own wording, to test genuine semantic matching rather than keyword overlap. Top result was excellent (found a passage about environmental/climate factors driving dengue, with zero exact word overlap with the query). Results 2-4 were topically relevant but looser matches. Result 5 was a chunk of the paper's *references list*, pulled in because citation entries are dense with topic words ("climate change", "dengue") without being real content.

**Known limitation, consistent with the earlier no-overlap decision:** naive fixed-size chunking has no awareness of document structure, so it can't distinguish real content from a references section. Candidate future fixes: strip reference sections before chunking, or document this as a real failing-case example in the eventual RAG evaluation writeup.

## 2026-07-31 — Step 5 complete: Streamlit v1, first real button-driven test of the full pipeline

Built `frontend/streamlit_app.py`: a workspace field, an upload form (PDF + metadata), a list of papers already in the workspace, and a raw-retrieval search box (no Claude-generated answer yet — that's Step 6). Three small backend wiring gaps surfaced by actually connecting the pieces for the first time (previously each was only exercised alone via its own `__main__` block):

- `insert_paper()` didn't return anything. The UI needs the new row's ID to tag that paper's chunks in Chroma, so it now returns `cursor.lastrowid` (SQLite hands back the auto-incremented ID right after an insert).
- `get_papers_by_workspace()` returned plain tuples, so reading a field meant a brittle positional index (`paper[1]`). Switched to `connection.row_factory = sqlite3.Row`, so callers can use `paper["title"]` instead — same data, safer to read, unaffected by future column reordering.
- Streamlit runs `frontend/streamlit_app.py` directly (never with `-m`), which hits the exact `ModuleNotFoundError` described in the 2026-07-28 entry above, since Python only knows about `frontend/`'s own folder by default. Fixed the same way: explicitly add the project root to `sys.path` at the top of the file (`sys.path.insert(0, str(Path(__file__).resolve().parent.parent))`) instead of relying on `-m`, which isn't available for how Streamlit invokes scripts.

Verified end-to-end in an actual browser (headless Chromium via Playwright, not just import-and-call): uploaded `data/sample.pdf`, got a success message with a real chunk count (81), saw it appear in the paper list, and ran a semantic search query that returned real matching text with distance scores. One real (harmless) surprise during testing: a raw `.fill()` into the search box produced zero results until the field lost focus — Streamlit's `st.text_input` only triggers a script rerun on blur or Enter, not on every keystroke, same category of "nothing happens until a deliberate submit" behavior as the upload form's submit button, just implicit here instead of an explicit form.

**Note on architecture:** at this step, `streamlit_app.py` calls `app/db`, `app/ingestion`, and `app/rag` functions directly, in-process — there's no HTTP boundary yet. `app/api/` (the FastAPI layer) was still planned for Step 6+ at this point, per `docs/project-structure.md`. This was an intentional in-between architecture, not a shortcut left to fix later.

**Deploy host and persistence decision, 2026-08-20:** researched deploy options beyond Streamlit Community Cloud (Render, Railway, Fly.io, Hugging Face Spaces). Verdict: none actually beat it while staying free — Render and Railway's free tiers have the same lack of persistent storage but sleep after 15 minutes vs. Streamlit Cloud's 12 hours (worse for a demo link), Fly.io dropped its free tier entirely in 2026 (needs a credit card even to trial), and Hugging Face Spaces is built more for ML model demos than a general app with a database. **Chose Streamlit Community Cloud, and chose to accept its ephemeral local storage (SQLite + Chroma files wiped on redeploy/sleep-wake) as a documented MVP limitation rather than solve it now** — the actual success criterion is a working, demoable, deployed app, which ephemeral storage satisfies fine within a single demo session; solving true persistence (migrate to an external hosted DB, or pay for a host with a mounted persistent volume — Railway Hobby at ~$5/mo is the cleanest, smallest-code-change option) is real, deferred to v2 in `CLAUDE.md`, revisit only if this needs to become an ongoing tool with data surviving across days/weeks rather than a portfolio/demo piece.

**Update, 2026-08-20 — `app/api/` deleted rather than left empty, while preparing for Step 8 (Deploy) and cleaning up the README/project-structure.md for the public repo.** Step 6+ came and went; the FastAPI boundary described above was never built, because nothing in the actual build ever needed it — one user, one Streamlit process, no second consumer of a backend API. Kept the empty scaffold folder around this whole time by default, not by decision. Revisited explicitly now: an empty folder implying planned-but-unstarted work is a worse signal in a public portfolio repo than no folder at all — if the FastAPI boundary genuinely becomes necessary later (a second frontend, independent scaling), it comes back with real code, not as a placeholder. `CLAUDE.md`'s stack line, `README.md`, and `docs/project-structure.md` all updated to match — this repo's docs shouldn't describe an architecture that doesn't exist.

## 2026-08-01 — Step 6 complete: RAG Q&A, the centerpiece, working end to end

Built the actual "ask a question, get a real answer" feature. Before writing code, described in plain English what the prompt to Claude should do — the answer was essentially the full spec already: use only the given excerpts, no outside knowledge, cite the paper, say "I don't know" instead of guessing. That became the system prompt almost verbatim; the only new API concept needed was the system/user message split (background instructions vs. the specific question).

**Citations required a real design decision, not just string interpolation.** First instinct was to store each chunk's paper *title* directly in Chroma alongside the chunk text. Caught before implementing: this would duplicate data that already lives in `papers.db` (title, authors, year), the same "two sources of truth" problem the `workspace`-column design was built to avoid back in Step 2. Fixed by storing each chunk's `paper_id` in Chroma instead (a real, queryable metadata field — previously only implicit in the id string like `"1-3"`), and adding `get_paper_by_id()` to `app/db/queries.py` so `generate_answer()` looks up the real title/authors/year at answer time. Citations now read like `"Climate Drivers of Dengue Transmission in Pakistan — A. Khan, S. Ahmed (2022)"` instead of a bare title.

**Environment/secrets setup:** created `.env` (real key, gitignored) and `.env.example` (placeholder, safe to commit) and verified the key worked with a live "say hello" test call before building anything on top of it. Real near-miss during setup: after revoking and regenerating the key, pasted the *new* key into `.env.example` instead of `.env` — the exact inversion of what the two files are for. Caught immediately (checked `git status`: the file was untracked, so nothing was ever exposed) and fixed by swapping the two files' contents.

**Cost check before building:** estimated ~$0.02/query on `claude-opus-4-8` (the CLAUDE.md default) given ~5 retrieved chunks (~5,000 characters ≈ 1,500–2,000 input tokens) plus a short cited answer (~200–300 output tokens) — meaning even 500 test queries would cost under $10. Considered Haiku for cost savings but kept Opus, since documenting failing queries (not just successful ones) in the eventual RAG evaluation writeup depends on the model actually being capable, so a cheaper model would blur "retrieval found the wrong chunks" (an interesting, real RAG limitation worth documenting) vs. "the model just isn't very good at following the citation instructions" (not what's being tested here).

**Verified in an actual browser**, not just a Python `__main__` block: asked "What is the economic burden of dengue?" against the real uploaded paper. Claude answered by quoting the paper directly, cited it correctly in the "Author, Year" format, and — for the part of the question the paper didn't have a specific number for — said so honestly instead of inventing a figure. That last part is the whole point of RAG's grounding instruction actually working, confirmed with a real query, not assumed from the code.

At this point extraction, chunking, embeddings, retrieval, *and* Claude-generated cited answers were all built and verified end to end. `docs/rag-evaluation.md` (10+ documented queries, 5 working + 3 failing) still not written — that's the remaining artifact, not the underlying capability.

## 2026-08-03 — Auto-detect paper metadata instead of typing it in manually

Real feedback from testing the app: "why do I need to type the title/authors — can't the AI figure that out?" Genuinely correct — the upload form was requiring manually retyping information already sitting in the PDF, contradicting the actual goal (upload a PDF, ask a question, nothing else). Root cause: `pypdf.extract_text()` only returns raw undifferentiated text; nothing had ever been built to recognize which part of that text is the title vs. the abstract vs. body text.

Fix: `app/ingestion/metadata_extractor.py` sends the first ~3000 characters of the extracted text to Claude with a structured-output schema (`output_config.format`, `json_schema`) covering title/authors/year/journal/doi/abstract, guaranteeing clean parseable JSON back instead of free-form prose. Real bug caught by testing before wiring it into the UI: the first attempt used `max_tokens=600` and got cut off mid-abstract (`stop_reason: "max_tokens"`) — abstracts are long. Fixed by raising to 1500.

UX decision (explicit tradeoff weighed): fully-silent auto-fill with no review step, vs. auto-filled-but-editable fields that can still be corrected. Chose the latter — a messy or unusually-formatted PDF could trip up extraction, and silently wrong metadata would undermine the same "cite accurately, don't guess" principle the RAG answers themselves rely on. Required moving `st.file_uploader` outside the form (so picking a file triggers an immediate rerun) and introducing `st.session_state` to cache the extracted text/metadata, keyed by filename, so re-running the script on every keystroke doesn't re-call Claude repeatedly.

Verified end-to-end in a real browser: uploading the actual sample PDF correctly auto-filled all six fields, including a full ~2000-character abstract, and correctly identified the paper as "Use of Expansion Factors to Estimate the Burden of Dengue in Southeast Asia" (Undurraga, Halasa & Shepard, 2013) — which incidentally revealed that the "Khan/Ahmed 2022" title/authors used in earlier manual test data was never actually accurate for this PDF's real content, just placeholder text typed in early in the project.

## 2026-08-03 — Real workspace pollution caught while testing the app, and a retrieval scaling risk it revealed

Asked "what factors facilitate the spread of dengue?" against a workspace containing one real paper (a Viruses/MDPI review on dengue genetic diversity) and got a thin answer. Investigated rather than guessed: `collection.get(where={"workspace": "abeer-test"})` showed `paper_id` 1 and 4 each had exactly 81 chunks — the *same* older test PDF, accidentally embedded twice under different IDs during this session's own testing. A 5-result search naturally returned near-duplicate top hits from both copies, leaving the one real, distinct paper (156 chunks) only one slot out of five. Confirmed the real paper actually had strong relevant content being crowded out — e.g. "The movement of extensive numbers of troops, an increase in global travel, and ecological disruption promoted the spread of mosquitoes..." — 22 of 156 chunks touched on spread-facilitating factors, none of which reached the answer.

Fix: added `delete_paper()` (queries.py) and `delete_paper_chunks()` (vector_store.py) — genuinely reusable CRUD completion, not one-off hacks — used them to remove the duplicate/placeholder papers (IDs 1, 2, 4), keeping only the real paper (ID 3). Also added `update_paper()` to fix that paper's metadata, which had come back empty (authors/year/journal/doi/abstract all `None`) because it was uploaded through an already-running browser tab still serving the pre-auto-extraction version of the app — not a bug in the new extraction code itself, confirmed by re-running `extract_metadata()` fresh and getting complete, correct data. Re-ran the original question after cleanup: real, correctly cited answer, matching the passage found during investigation.

**Forward-looking risk, explicitly scheduled rather than left to drift:** the crowding mechanism here was caused by an accidental literal duplicate, but the same mechanism — a fixed `n_results=5` letting a couple of chunks dominate all return slots — would recur with genuine topic overlap once the workspace has many real papers on similar subjects, not just duplicates. Decision: don't build `n_results` tuning or diversity-aware retrieval now, with only one real paper to test against — fold it into the already-deferred `rag-evaluation.md` task instead. When those ~10 real papers are uploaded, deliberately test a broad multi-paper-relevant question as part of that eval; if crowding recurs for real, it becomes one of the 3 documented failing queries and the tuning work becomes evidence-driven rather than speculative.

## 2026-08-19 — `docs/rag-evaluation.md` written; closes two loops deferred earlier with real evidence

Ran 10 real questions against the `abeer-test` workspace (6 working, 4 failing — exceeds the 5+3 minimum target). Every claim in every write-up, both successes and failures, was independently re-verified against the actual PDF text before being recorded — caught one near-miss where a body-text finding looked like it contradicted a paper's own abstract, resolved by finding both were separately true (different comparisons reported in the same study), not an error.

This directly closes two things this file explicitly deferred pending real evidence, rather than fixing speculatively:
- **The 2026-07-24 entry above** ("revisit [chunking overlap] if retrieval quality later seems to miss things right at chunk boundaries") — confirmed for real: a paragraph in paper 9 (TAK-003, T-cell/B-cell immune response detail) was split mid-word by the fixed-1000-character chunker, contributing to an incomplete answer.
- **The 2026-08-03 entry** (`n_results=5` crowding, deferred until a genuine multi-paper-overlap corpus existed) — confirmed for real, twice: paper 12's chunks crowded out paper 9's relevant chunk on a TAK-003 question, and a single large 281-chunk document (the WHO guidelines) got so diluted by its own front-matter that none of its 62 substantively relevant chunks were retrieved for a severe-disease-management question.

One new failure mode not previously flagged: a font-encoding problem specific to one source PDF (`ns1.pdf`, paper 13) corrupted its extracted text badly enough (`"further"` → `"fu r t h er"`) to degrade that paper's embeddings — none of its chunks were retrieved for a question its content directly answers. Combined with the chunk-boundary and crowding findings, this became the concrete justification for the structure-aware-ingestion v2 item added to `CLAUDE.md` (PDF → clean Markdown before chunking, instead of raw `pypdf` text).

## 2026-08-20 — Step 7 Polish: workspace picker, delete button, and revisiting the `workspace`-not-auth tradeoff

Three real rough edges found through actual use got fixed: (1) `data/uploads/` had files scattered across two inconsistently-named subfolders from earlier bulk-ingestion runs plus loose files at the top level — flattened to one consistent directory, and one filename (`diagnostic accuracy.pdf` → `diagnostic_accuracy.pdf`) had its database record updated to match the rename, since the two had drifted out of sync; (2) the workspace field was a free-text box with no way to see what workspaces already existed — replaced with `st.selectbox` (`get_all_workspaces()`, `SELECT DISTINCT workspace FROM papers`) with an "Add new workspace" escape hatch for genuinely new names; (3) `delete_paper()`/`delete_paper_chunks()` existed since 2026-08-03 but were never wired into the UI — added, with both database and vector-store deletion firing together so nothing gets orphaned in Chroma.

**Revisited the `workspace`-not-auth decision (originally made Step 2, logged in `docs/db-review-log.md`) in light of delete now existing.** The original reasoning still holds — this is a single-user app, `workspace` was only ever meant for organizing one person's own projects, not for keeping separate people's data apart. But adding delete changes the stakes of that same tradeoff: reading another workspace's data is low-risk and reversible; deleting from one is destructive and irreversible. Two things followed from that distinction:
- **Shipped now:** a confirm-before-delete step (two-click pattern via `st.session_state` as an armed/unarmed flag, not just a data cache) — cheap, and protects against accidental clicks regardless of who's using the app.
- **Explicitly deferred, not forgotten:** real access control (a `users` table, login, a `user_id`/`owner` column on `papers` instead of just `workspace`) is a decision that has to be made before Step 8 (Deploy), not before now — once this app has a real public URL, "no auth" stops being a private single-user assumption and becomes a real exposure. Simplest fix at that point is a lightweight password gate, not full accounts.

Also considered and explicitly deferred to v2: a real recycle bin (soft delete via a `deleted_at` column + restore by re-running the full ingestion pipeline, since Chroma embeddings would need re-creating, not just un-flagging). Scoped down to the cheaper confirm-before-delete step instead, which covers the actual risk (accidental irreversible deletion) without a schema migration or new UI section — a deliberate "smaller fix, same risk covered" call, not a shortcut.

## 2026-08-23 — Staging environment adopted, flagged too late to catch it before the fact

Genuine process miss, worth recording honestly rather than glossing over: the need for a staging environment was recognized in principle before any deploy work started, but wasn't actually acted on until after several pushes had already gone straight to production, including a real ImportError incident. Caught directly, with the question of why it wasn't flagged proactively, before it could have actually been practiced live instead of only adopted in hindsight.

Root cause: the remaining deploy-adjacent docs were treated as one batch of "documentation to write after the deploy," without distinguishing that some of them (SLA definition, escalation protocol) can only honestly be written *after* living the deploy experience, while staging is a workflow habit that only has real value if adopted *before* the risk, not retrofitted afterward. The same sequencing logic got applied to two genuinely different kinds of task.

**Adopted going forward, can't undo the deploys that already happened:** created a `staging` branch and a second Streamlit Community Cloud app pointed at it (free — Streamlit Cloud allows multiple public apps, no cost like the persistence question). Real code changes now go to `staging` first, get verified on its separate URL, and only get merged into `main` (which production tracks) once confirmed working. Docs-only changes still go straight to `main`, since they carry no behavior risk — applying the practice indiscriminately would be following the letter of it without the actual reasoning.

Worth naming as its own lesson, distinct from the staging practice itself: **tasks grouped under one project step aren't automatically safe to batch and defer to "after" that step is done** — some are genuinely retrospective (write about what happened), some are genuinely prospective (adopt before it happens). Check which kind before sequencing, not just which step a plan assigned it to.
